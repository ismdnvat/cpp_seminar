Почему папка, а не один файл

Переход к определению, поиск по проекту и сборка настраиваются на папку. Если открыть одиночный .cpp, половина возможностей просто молчит — и кажется, что «у меня не работает».

То же самое в CLion

Проект — папка с CMakeLists.txt. Собрать — Ctrl+F9, запустить — Shift+F10, терминал — Alt+F12, ошибки — окно Build.

Кнопка сборки в любом случае запускает компилятор. Какую именно команду — видно в tasks.json у VS Code и в окне Build у CLion.

Ответ

Разложим по полочкам

Компилируемый

Текст превращается в машинный код заранее, отдельной программой-компилятором. Запускается уже готовый файл, а не исходник.

Со статической типизацией

Тип переменной известен до запуска и не меняется. Компилятор проверяет операции при сборке.

Со строгой типизацией

Сам по себе int в строку не превратится: нужно явно попросить преобразование.

Быстрый и близкий к железу

Нет промежуточного слоя вроде интерпретатора, нет сборщика мусора. За скорость платим вниманием: за границы массива никто не поругает.

С ручным управлением памятью

Программист решает, где живут данные и сколько. Это и сила, и источник целого класса ошибок.

Стандартизованный

Язык описан документом — стандартом, версии выходят раз в три года: C++17, C++20, C++23. Компиляторов много: g++, clang++, MSVC.

Многопарадигменный

Можно писать процедурно, объектно, обобщённо через шаблоны — и всё это в одном файле.

Совместимый с C

Почти весь код на C — валидный C++. Отсюда и наследие вроде printf, и две традиции в одном языке.

Типы

Тип переменной известен заранее — и это меняет всё

#include <iostream>

int main() {
    int n = 0;
    double x = 0;
    std::cin >> n >> x;
    std::cout << "n=" << n << " x=" << x << '\n';
}
на вход подали 3.7 3.7 — что напечатает?
$ printf '3.7 3.7\n' | ./types_read n=3 x=0.7

>> читает в тип: для int берёт только 3 и останавливается на точке, оставив .7 в потоке. Следующее чтение — уже в double — забирает .7.

Тип задаётся один раз и не меняется

  • переменная объявляется вместе с типом: int n = 0;
  • дальше меняется только значение, тип остаётся навсегда
  • компилятор проверяет все операции до запуска — значит часть ошибок вы видите при сборке, а не на тестах
int count; ... count = "много"; 
type_err.cpp: In function ‘int main()’:
type_err.cpp:6:13: error: invalid conversion from ‘const char*’ to ‘int’ [-fpermissive]

Цена — тип надо выбрать заранее и помнить о нём: int и double делятся по-разному, int переполняется, size() возвращает беззнаковое.

Ввод

Как читается ввод в C++

#include <iostream>

int main() {
    int a = 0;
    int b = 0;
    int c = 0;
    std::cin >> a >> b >> c;
    std::cout << a + b + c << '\n';
}
$ printf '1 2 3\n' | ./read3 6 $ printf '1\n2\n3\n' | ./read3 6 $ printf ' 1 2\n\n 3\n' | ./read3 6

Что делает >>

  • пропускает всё пустое перед значением: пробелы, табы, переводы строк
  • читает столько символов, сколько подходит под тип слева
  • сам превращает текст в int или double
  • останавливается на первом неподходящем символе и оставляет его в потоке

Что из этого следует

  • для >> перевод строки — такой же разделитель, как пробел: три запуска выше дают один ответ
  • сколько переменных перечислили — столько значений и прочитается
  • та же программа читает данные из файла: ./read3 < input.txt

Разбирать строку символ за символом приходится, когда разделители не пробельные — например время 12:30:05. Тогда читают строку целиком и разбирают её.

Ввод

Читаем, пока читается

#include <algorithm>
#include <iostream>
#include <vector>

int main() {
    std::vector<int> numbers;
    int x;
    while (std::cin >> x) {
        numbers.push_back(x);
    }

    std::sort(numbers.begin(), numbers.end());

    for (int value : numbers) {
        std::cout << value << ' ';
    }
    std::cout << '\n';
}
$ printf '5\n3\n9\n' | ./tasks/t00_sort 3 5 9

Почему это работает

std::cin >> x читает число и возвращает сам поток std::cin. В условии поток проверяется как логическое значение: true, если последнее чтение прошло успешно.

На конце ввода — Ctrl+D — или на слове, которое не число, поток переходит в состояние ошибки, и условие становится ложным.

Пробелы не важны

>> сам пропускает пробелы, табы и переводы строк. Числа в строку и числа в столбик читаются одинаково.

Вывод

Вывод: что печатается и как

#include <iostream>

int main() {
    int count = 7;
    double average = 1.0 / 3;

    std::cout << "count=" << count << " average=" << average << '\n';
    std::cout << 100000000.0 << '\n';
    std::cout << 2 / 3 << ' ' << 2.0 / 3 << '\n';
}
$ ./print_basics count=7 average=0.333333 1e+08 0 0.666667

Три вещи, которые удивляют

  • пробелы между значениями не появляются сами — их печатают: << ' '
  • double печатается с шестью значащими цифрами, большие числа — в виде 1e+08
  • 2 / 3 — целочисленное деление, ноль. Дробь получится только если хотя бы одно число дробное

'\n' или std::endl

std::endl — это перевод строки плюс принудительный сброс буфера на экран. В циклах на сотни тысяч строк это заметно медленнее. Привычка простая: пишем '\n', а std::endl — только когда действительно нужно, чтобы текст появился немедленно.

Ответ

Ответ: кто что прочитал из буфера

что произошло
std::cin >> age;
std::getline(std::cin, name);
$ printf '19\nАнна Петрова\n' | ./getline_trap age=19 name=[]
19⏎Анна Петрова⏎
прочитал >>прочитал getline (⏎ выброшен)осталось непрочитанным

>> читает 19 и останавливается перед ⏎. getline читает символы до первого ⏎ и выбрасывает его — а он идёт сразу. Строка пустая, «Анна Петрова» так и осталась в потоке.

как починить
std::cin >> age;
std::cin.ignore(10000, '\n');
std::getline(std::cin, name);
$ printf '19\nАнна Петрова\n' | ./getline_fix age=19 name=[Анна Петрова]
19⏎Анна Петрова⏎
прочитал >>выброшен ignoreпрочитал getline (⏎ выброшен)

ignore выбрасывает из потока всё до конца строки включительно — здесь это тот самый ⏎. После этого getline видит имя и читает его до следующего ⏎. Первый аргумент — «не больше стольких символов», он просто большой.

getline нужен, когда в строке есть пробелы. Для чисел и отдельных слов хватает >>. Короткая форма std::cin.ignore() убирает ровно один символ — её хватает, когда после числа сразу Enter, но она ломается, если в конце строки остались пробелы.

Разминка

Разминка: сумма и максимум

Числа идут до конца ввода, сколько их — заранее неизвестно. Семь минут.

Что написать

  • читать числа, пока читаются
  • напечатать, сколько чисел прочитано, их сумму и максимум

Проверить можно на файле из архива: ./warmup < tasks/t0_input/input.txt. С клавиатуры конец ввода — Ctrl+D.

ввод
4 15 8 23 42 16
вывод
чисел: 6, сумма: 108, максимум: 42
#include <iostream>
#include <limits>

int main() {
    int x = 0;
    int total = 0;
    int best = std::numeric_limits<int>::min();
    int count = 0;

    while (std::cin >> x) {
        total += x;
        if (x > best) {
            best = x;
        }
        count += 1;
    }

    std::cout << "чисел: " << count << ", сумма: " << total << ", максимум: " << best << '\n';
}

Максимум нельзя начинать с нуля: если все числа отрицательные, ответ будет неверным. Берут либо первое прочитанное число, либо std::numeric_limits<int>::min() — минимум того же типа, что и переменная.

Кто что делает

Кнопка «запустить» — это не компилятор

IDE (VS Code, CLion)

  • редактор с подсветкой и автодополнением
  • кнопка, которая за вас набирает команду в терминале
  • показывает ошибки в удобном виде
  • сама ничего не компилирует

Компилятор (g++, clang++)

  • отдельная программа на вашем компьютере
  • превращает текст в исполняемый файл
  • вся правда — в его командной строке и флагах
  • работает одинаково из IDE и из терминала
$ g++ --version g++ (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0 $ which g++ /usr/bin/g++
Где живёт компилятор

Где в редакторе спрятан компилятор

VS Code: два разных места

  • tasks.json, поле "command" — чем собирается проект. Обычно /usr/bin/g++, рядом в "args" — флаги.
  • c_cpp_properties.json, поле "compilerPath" — только для подсветки и автодополнения. На настоящую сборку не влияет.

Отсюда частая путаница: в настройках выставлен C++20, а собирается всё равно старым стандартом — потому что правили не тот файл.

Стандарт

Стандарт надо просить явно

Макрос __cplusplus компилятор подставляет сам — в нём номер версии стандарта, по которому идёт сборка.

$ g++ std_version.cpp -o sv $ ./sv 201703 это C++17 $ g++ -std=c++20 std_version.cpp -o sv $ ./sv 202002 а это C++20

Что запомнить

  • у компилятора есть версия (у нас 13.3.0) и стандарт, по которому он собирает
  • по умолчанию стандарт — не самый свежий
  • нужен конкретный стандарт — указывайте его флагом -std=

Как выглядит команда с флагами

$ g++ -std=c++20 -Wall -Wextra main.cpp -o main
Четыре стадии

Одна команда — четыре программы

Когда вы пишете g++ main.cpp -o main, по очереди отрабатывают четыре стадии. Обычно их не видно, но каждую можно запустить отдельно.

report.cppто, что написали вы
-Eпрепроцессор
report.iiтекст после препроцессора
-Sкомпиляция
report.sассемблер
-cассемблирование
report.oмашинный код, но без адресов
g++ *.oлинковка
программаеё можно запустить

Зачем это знать

  • ошибки на разных стадиях выглядят и чинятся по-разному
  • undefined reference — это не компилятор, это линковщик
  • большие проекты собираются по файлам: изменил один .cpp — пересобрался один .o

Флаги-остановки

-Eостановиться после препроцессора
-Sостановиться после компиляции, получить ассемблер
-cостановиться после ассемблирования, получить .o
-o имякак назвать результат

Препроцессор

Препроцессор не знает C++

Он работает с текстом: вставляет файлы, подставляет макросы, выкидывает куски. Про типы, функции и синтаксис он не знает ничего.

Что он умеет

#includeвставить содержимое файла прямо сюда
#defineзаменять один текст другим
#ifdef / #ifоставить или выкинуть кусок кода
#pragma onceне вставлять этот файл второй раз

#include — буквальная вставка

#include <iostream> ищет файл в системных каталогах, #include "geometry.h" — сначала рядом с вашим файлом.

Именно поэтому строк стало 36 587: текст вставился целиком, со всеми вложенными include.

Как посмотреть результат

$ g++ -E main.cpp | tail -20

Ваш код — в самом конце. Отладка макросов начинается с этой команды.

error

Компилятор не может собрать программу. Файла на выходе не будет. Чинить обязательно.

warning

Ответ

А теперь попросим компилятор посмотреть внимательно

warn.cpp:7:23: warning: comparison of integer expressions of different signedness: ‘int’ and ‘std::vector<int>::size_type’ {aka ‘long unsigned int’} [-Wsign-compare]

флагчто даёт
-Wallнабор самых полезных предупреждений. Вопреки названию — не все

Почему падает

Функция обязана вернуть int, но на одном из путей не возвращает ничего. Это undefined behavior; g++ ставит в это место инструкцию, которая аварийно завершает программу — отсюда Illegal instruction.

Уровни -O

Что произойдёт?

Компилятор не ругался: объявление он видел в geometry.h. А линковщик искал тело функции и не нашёл — geometry.cpp ему не дали.
Ответ

undefined reference — это линковщик

$ g++ main.cpp -o app
ld: main.o: in function `main':
main.cpp:(.text+0x13): undefined reference to `area(int, int)'
collect2: error: ld returned 1 exit status

Слово ld в начале — это и есть линковщик. Если видите его в ошибке, значит компиляция прошла успешно и проблема в другом.

nm объясняет всё
$ nm -C main.o | grep area U area(int, int) $ nm -C geometry.o | grep area 0000000000000000 T area(int, int)

Как читать

  • U в main.o — «мне нужна area, я не знаю где она»
  • T в geometry.o — «area у меня, вот код»
  • линковщик соединяет U с T. Нет пары — ошибка

Три причины undefined reference

  • забыли передать .cpp или .o в команду сборки
  • объявили одно, определили другое: опечатка в имени или другие типы аргументов
  • объявили функцию и не написали тело вовсе
Заголовки

Почему нельзя include-ить .cpp

тело функции положили в заголовок... 
// geometry.h
#pragma once

int area(int width, int height) {
    return width * height;
}
...и подключили его из двух разных .cpp
$ g++ -c main.cpp -o main.o $ g++ -c helper.cpp -o helper.o $ g++ main.o helper.o -o app
ld: helper.o: in function `area(int, int)':
helper.cpp:(.text+0x0): multiple definition of `area(int, int)'; main.o:main.cpp:(.text+0x0): first defined here
collect2: error: ld returned 1 exit status

Что произошло

Каждый .cpp компилируется отдельно и получает свою копию тела функции. Линковщик видит два определения одного имени и не знает, какое брать.

#pragma once в начале заголовка просит препроцессор не вставлять этот файл в один и тот же .cpp дважды. Здесь он не помогает: файла два, и в каждый тело попало по одному разу.

Правило

  • в .h — объявления: int area(int width, int height);
  • в .cpp — определения, то есть тела
  • #include "что-то.cpp" — не делаем никогда

Зачем компилятор так делает

В C++ можно объявить несколько функций с одним именем и разными параметрами. Линковщик про перегрузки ничего не знает — он работает с именами. Поэтому компилятор зашивает типы аргументов прямо в имя.

Практическое следствие

Ошибка undefined reference всегда печатает полную сигнатуру. Если она не совпадает с тем, что вы определили, — вы объявили и определили разные функции.

Запас

Ворнинг, которого нет ни в -Wall, ни в -Wextra

#include <iostream>

int main() {
    int count = 5;
    for (int i = 0; i < 3; ++i) {
        int count = i;
        std::cout << count << ' ';

}
$ g++ -Wall -Wextra -c shadow.cpp тишина $ g++ -Wall -Wextra -Wshadow -c shadow.cpp shadow.cpp:6:13: warning: declaration of 'count' shadows a previous local [-Wshadow]

Почему это важно

Внутренняя переменная закрывает внешнюю. Код компилируется, работает — и делает не то, что вы думали, когда читали его глазами.

Отсюда мораль: наборы -Wall -Wextra — не «все предупреждения». Полезные флаги есть и за их пределами.
